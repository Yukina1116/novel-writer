## セッション要旨

### 1. 課金プログラムの振り返りと、アーキテクチャ予定の確認(会話上の報告)

ADR-0001・dev ポータル・価格メモ・決済基盤メモ・現行コードを突き合わせ、方針と論点を整理した。主な指摘:

- **有料枠の赤字リスク**: 案 A(¥980、AI 上限は Tier 1 の 30 倍 = 3,000 円相当)は、手取り(約 ¥850〜905)を上回る。上限まで使うユーザー 1 人で赤字。暫定で Tier 1 の 5 倍(50,000 sen)を推奨
- **価格メモの前提が古い**(下記「却下候補」参照): Imagen 前提の 10 円/回、Stripe 手数料の記載の食い違い
- **M6.5(Cloud Storage)が M5 より後**のため、初期の Tier 2 は AI 枠のみになる
- **課金の設計上の論点**: `users.plan` の enum を広げると client が自分で有料化できる / Webhook は `express.json` より前に raw body が必要 / 順序逆転・重複配信 / 期限管理 / Secret 管理
- **税務・事業主体が未整理**(課税事業者・インボイス登録の有無、販売主体)

### 2. ADR-0004 の起草(方針の変遷)

オーナーの方針(「Stripe は最もシンプルに」「ほぼ個人開発(2 名以下)なので過剰にしない」「通常の流れは完全自動化」「実装はまだしない」)に沿って、次のように絞り込んだ。

- 購入は **Payment Link**、契約管理は **コード不要のカスタマーポータル**。自前の課金 API は **Webhook 1 本のみ**
- 課金状態は `billing/{uid}`(client 書込み全拒否)に分離。`users.plan` は `['free']` のまま触らない
- Webhook は Stripe から Subscription を取り直して上書き(冪等)。`stripeEvents` コレクションは作らない(ADR-0001 からの変更点)
- Tier は `status` と `currentPeriodEnd` から導出(期限で自然失効)。失敗の検知(構造化ログ + 既存 Cloud Logging アラート)を最優先
- 公式 docs で確認: Payment Link の `client_reference_id` は Webhook で返る / カスタマーポータルはコード不要 / Stripe API 2025-03-31.basil 以降 `current_period_end` は subscription item 側
- 工数は 1.5〜2 人日程度の見込み(設計時点の見積もり、実測ではない)

### 3. 詳しさのレベル感の食い違いと、その解消

オーナーから「まだシステムへ実装しない。dev ポータルに書くレベルまでの内容だった」との指摘。ADR-0004 はエンドポイント名・環境変数名・rules まで書いた**実装仕様寄り**で、合意が取れていなかった(オーナーが確認していたのは大きな方針の部分)。#318・#319 で「構想・実装前。細部は M5 着手時に公式 docs で再確認」を ADR とポータルに明記して解消した(細部は削らず維持)。
